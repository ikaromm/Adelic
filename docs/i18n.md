# Interface language (i18n)

Adelic's UI is available in Brazilian Portuguese (`pt-BR`, the source language) and English (`en`). This page explains how
translations work and how to convert a component. The code has no i18n dependency: the core is `shared/i18n.ts`, shared by
the UI (`src/i18n/`) and the server (`server/i18n.ts`).

## Choosing the language

- `Settings.language` is `'auto' | 'pt-BR' | 'en'` (absent = `auto`), saved on the server and changed in Settings › Geral ›
  "Idioma / Language" (the first card). `auto` uses `navigator.language`: any `pt*` → pt-BR, anything else → English.
- The choice is mirrored in `localStorage` (`adelic-language`), so the login screen (before any API access) and the first
  paint after a reload already use it. `<html lang>` follows the resolved locale.
- E2E specs pin the browser to `pt-BR` (`playwright.config.ts`), so `auto` keeps resolving to Portuguese there.

## UI API

```tsx
import { useI18n } from '../i18n';

function SaveBar({ count, updatedAt }: { count: number; updatedAt: string }) {
  const { t, tRich, fmt, locale } = useI18n();
  return (
    <p title={fmt.dateTime(updatedAt)}>
      {t('chat.files', { count })} · {fmt.relative(updatedAt)}
      {tRich('chat.contextOf', { project: <strong>Adelic</strong> })}
    </p>
  );
}
```

- `t(key, vars?)` returns a string. `{name}` is replaced by `vars.name`; an unknown placeholder stays visible.
- Plurals: define `x.one` and `x.other` (optionally `x.zero`) and call `t('x', { count })`. The category comes from
  `Intl.PluralRules` (note: in pt-BR, 0 is `one`; add `x.zero` when "nenhum" reads better).
- `tRich(key, vars)` is for markup inside a sentence; values may be React nodes. Render the returned array.
- `fmt` formats in the current locale: `duration`, `relative`, `tokens`, `runTokens`, `cost`, `number`, `time`,
  `shortDate`, `dateTime`. The same helpers are exported from `src/format.ts` with an optional `locale` argument.
- Outside components (plain modules, callbacks that run outside render): `import { t, fmt, getLocale } from './i18n'`.
  They read the module-level locale store that `useI18n()` subscribes to. Do not call the plain `t()` at module top
  level: the result would be frozen in the locale at import time. Wrap it in a function (see `modeLabel` in
  `src/ComposerMenus.tsx`).
- `useI18n()` needs no provider.

## Catalog areas

Messages live in `src/i18n/messages/<area>.ts` (UI) and `server/i18n/messages/<area>.ts` (server), one file per area, so
parallel work does not conflict:

```ts
import { defineMessages } from '../../../shared/i18n';

// Chat transcript (src/components/Chat.tsx).
export default defineMessages(
  {
    'chat.copy': 'Copiar',
    'chat.files.one': '{count} arquivo',
    'chat.files.other': '{count} arquivos',
  },
  {
    'chat.copy': 'Copy',
    'chat.files.one': '{count} file',
    'chat.files.other': '{count} files',
  },
);
```

- The pt-BR object is the source of truth. `defineMessages` types `en` as `Record<keyof ptBR, string>`, so a missing or
  extra English key is a compile error. `tests/i18n.test.ts` also checks key sets, empty strings, matching placeholders and
  keys duplicated across areas.
- Keys are `<area>.<name>` (e.g. `settings.remote.title`), camelCase segments. Each key lives in exactly one area. Shared
  vocabularies have their own prefixes: `common.*`, `mode.*`, `thinking.*`.
- Register the area in `messages/index.ts` with one line, kept in alphabetical order:
  `export { default as chat } from './chat';`. Keys are typed from that file, so `t('chat.copy')` is checked.

Existing areas: UI `auth` (login screen), `common`, `composer`, `settings`, `shell` (header and connection badge), `sidebar`;
server `auth`, `common`, `remote`.

## Converting a component (checklist)

1. Pick an area name for the file or group (`chat`, `activity`, `memory`, `remote-access` → `remoteAccess.*`). Create
   `src/i18n/messages/<area>.ts` and add its line to `src/i18n/messages/index.ts`. Touch no other area file.
2. Move every user-visible string (text, `aria-label`, `title`, `placeholder`, `alt`, toasts, `Error` messages shown in
   the UI) into the pt-BR object, **byte-identical**: same accents, punctuation, `…`, `›`, non-breaking spaces. E2E specs
   assert this text.
3. Write the English entry for each key. Keep product and tool names as they are (Adelic, Codex, Claude, Kiro, Graphify,
   Tailscale, Funnel, tailnet, voxtype, ai-memory, MCP, Skills), and keep slash commands (`/plano`), env vars and file
   paths unchanged.
4. In the component, `const { t, fmt } = useI18n();` and replace each literal with `t('area.key', vars)`. Replace
   `toLocaleString('pt-BR')` and the `src/format.ts` / `src/labels.ts` helpers with `fmt.*`.
5. Run `npx tsc --noEmit`, `npx vitest run tests/i18n.test.ts`, the component's E2E spec, and check the screen in English
   (Settings › Idioma / Language).

## Rules

- Never build a sentence by concatenating translated pieces (`t('a') + name + t('b')`): word order differs between
  languages. Use one key with placeholders, or `tRich` for markup.
- Labels with a fixed separator (`Leitura · Auto`) are one key each, not two joined at runtime.
- Plurals always go through `count`, never `n === 1 ? … : …`.
- Do not translate data: conversation titles, messages, model names, file paths, provider output and persisted run events.
- Keep pt-BR identical when moving text. If the Portuguese wording should change, do it in a separate change and update the
  specs that assert it.

## Server messages

The client sends `Accept-Language: <locale>` on every API call (`src/api.ts` `request()`, and the login screen). An
`EventSource` cannot set headers, so stream URLs go through `eventsUrl()`, which adds `?lang=<locale>`.
`localeMiddleware` (mounted right after request classification in `server/index.ts`) sets `req.locale` with `?lang=`
first, then the best supported `Accept-Language` tag. Without one, the server answers in pt-BR as before.

```ts
import { error } from './common.js';
import { LocalizedError, tr } from '../i18n.js';

error(res, 404, 'remote.sessionNotFound'); // a catalog key, translated per request
error(res, 400, 'projects.tooLong', { max: 200 }); // key + vars
error(res, 400, 'Projeto não encontrado'); // plain string: sent unchanged (not converted yet)
throw new LocalizedError('remote.accountFirst', undefined, 409); // from services, outside a request
tr(req.locale, 'auth.required'); // the text itself
```

- `error()` translates a string only when it is a known key (keys never contain spaces), so unconverted routes keep
  working.
- `LocalizedError.message` is the pt-BR text (logs, older tests); `failure()` and `error()` translate it again to the
  request's locale.
- `parseBody(schema, body, fallback)` passes its fallback to `error()`, so the fallback can be a key too.
- `server/http/auth.ts` and `server/http/remote-access.ts` are the converted examples.
- Persisted run events, activity entries and messages stay in the language they were produced in. They are history and
  are never translated again when the locale changes. Only new responses follow the request's locale.
